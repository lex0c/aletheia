# Servidores de teste (fixtures)

Tres Dockerfiles que representam o **disco** de tres maquinas Linux de producao
diferentes, cada uma administrada por gente competente e cada uma com o acumulo
de historia que uma maquina real tem: logs rotacionados, cron, backup, agente de
telemetria, script solto em `/usr/local/sbin`, config antiga que ninguem removeu.

```sh
docker build -f Dockerfile.web   -t servidor-web:test   .
docker build -f Dockerfile.db    -t servidor-db:test    .
docker build -f Dockerfile.build -t servidor-build:test .
```

Nenhum deles tem systemd como PID 1. As units ficam **no disco** (com os symlinks
de `multi-user.target.wants`, drop-ins e units mascaradas), que e o que importa
para inspecionar configuracao. O `CMD` e `/bin/bash`.

| arquivo | base | papel | estilo |
|---|---|---|---|
| `Dockerfile.web` | debian:12 | nginx + gunicorn (Flask) | arrumado, recem reconstruido |
| `Dockerfile.db` | rockylinux:9 | PostgreSQL 16 primario | **bagunçado**: MySQL -> 9.6 -> 13 -> 16 |
| `Dockerfile.build` | ubuntu:22.04 | agente de build Jenkins (SSH) | VM de nuvem, cheia de cache |

## Dockerfile.web — `app-web-03.prod.example.net`

Debian 12, o no de web mais novo do pool. Deploy no esquema
`releases/` + `current` (estilo Capistrano), que e como a maioria dos deploys por
SSH ainda funciona.

**Servico e runtime**
- `nginx` do pacote, com `sites-available`/`sites-enabled`, `conf.d/` numerado
  (`00-log-format`, `10-gzip`, `30-limits`), `snippets/` reutilizaveis
  (`ssl-params`, `security-headers`, `proxy-app`) e um vhost interno na 8080 com
  `stub_status` + `.htpasswd`. `nginx -t` roda no build, entao a config e valida.
- Python 3 + **virtualenv de verdade** em `/srv/app/shared/venv` com Flask e
  gunicorn instalados do PyPI. O app importa (`wsgi:application` sobe).
- Tres releases datadas em `/srv/app/releases/`, `current` apontando para a mais
  nova, `REVISION`/`DEPLOYED_AT` em cada uma, `shared/` com config, uploads, log,
  sockets e pids, e os symlinks (`.env`, `log`, `uploads`) que o deploy cria.

**Por que e realista**: ninguem deixa o codigo em `/opt/app` solto. O par
`shared/` + `releases/` + `current` existe porque rollback tem que ser um
`ln -sfn`, e o venv fica em `shared/` para nao reinstalar tudo a cada deploy.

**Contas**: `app` (system, nologin, dono do codigo), `deploy` (o CI entra por
SSH), dois humanos no grupo `sudo`, `bkpsvc` com `ForceCommand` que so aceita
`rsync --server --sender`, `www-data` no grupo `app`. Sudoers por `Cmnd_Alias`,
nao `NOPASSWD: ALL` — validado com `visudo -c` durante o build.

**SSH**: hardening em `sshd_config.d/10-hardening.conf` (o arquivo do pacote fica
intocado, que e o ponto do `Include`), host keys geradas, `authorized_keys` para
cada usuario, `ssh_known_hosts` com bastion e git, `Match Group bkpsvc`.

**systemd no disco**: `app.service` (com `ProtectSystem=strict`, `ReadWritePaths`,
watchdog), `app.socket`, `app-worker.service`, `app-housekeeping.service`+`.timer`,
drop-in de `LimitNOFILE` para o nginx, e os symlinks de enablement.

**Cron**: `/etc/cron.d/` (backup, certbot, housekeeping, textfile), um
`/etc/cron.daily/logship`, e crontabs de usuario em `/var/spool/cron/crontabs/`
com dono `user:crontab`, modo 600 e o cabecalho "DO NOT EDIT THIS FILE" que o
`crontab -e` escreve. O crontab do root tem o classico restart semanal com
comentario apontando o incidente que o motivou.

**Logs**: dois formatos, porque o nginx.conf do pacote e o vhost declaram coisas
diferentes — `access.log` sai no `combined` classico (660 linhas geradas) e
`loja.access.log` sai no `json_combined` definido em `conf.d/00-log-format.conf`
(600 linhas, cada uma parseavel por `jq`, com `rt`/`urt`/`xff`). Os dois tem `.1`,
`.2.gz`, `.3.gz` com mtimes antigos — **evidencia de rotacao**, nao so a policy.
Tambem `error.log` dos dois vhosts, logs do app em JSON, `deploy.log` (inclusive
um rollback automatico apos healthcheck 502), `auth.log` com tentativa de invasao,
`fail2ban.log` com o ban correspondente, `apt/history.log`,
`unattended-upgrades.log` e `/var/lib/logrotate/status` preenchido.

**TLS**: certificado **autoassinado**, mas arquivado exatamente como o certbot
deixa: `archive/dominio/cert3.pem` + symlinks em `live/` + `renewal/*.conf` com
`renew_hook`. Ferramenta que percorre essa arvore se comporta normalmente.

**Fora do gerenciador de pacotes**: `/opt/telemetry-agent/` no formato tarball de
fornecedor (`bin/`, `conf.d/`, `VERSION`, `install_info` dizendo quem instalou e
quando), com usuario proprio, config em `/etc/telemetry-agent/agent.yaml`, unit e
logrotate; e `/opt/venvs/ops` para ferramenta ad-hoc do time. O agente e um script
Python que funciona de verdade (le `/proc`), nao um binario falso.

**Disco e rede**: `/etc/fstab` com `/var` e `/srv` em LVs proprios (uploads nao
podem derrubar a raiz), `/tmp` em tmpfs e um NFS de uploads; `/etc/network/interfaces`
com IP estatico e `interfaces.d/`, do jeito Debian.

**Resto**: `prometheus-node-exporter` com textfile collector populado
(`deploy.prom`, `backup.prom`, `ssl.prom`), fail2ban com jail local, msmtp como
relay, chrony, unattended-upgrades com blacklist do nginx, `sysctl.d`,
`limits.d`, `profile.d`, backups em `/var/backups/app/` com manifesto sha256,
`rsyslog` mandando para o coletor central, `/etc/ansible/facts.d/`, notas do
admin em `/root`, `.bash_history` plausivel.

## Dockerfile.db — `db-01.prod.example.net`

Rocky 9 com PostgreSQL 16 do module stream do AppStream. **Esta e a maquina
suja**: nasceu CentOS 7 com MariaDB, virou PostgreSQL 9.6, foi reconstruida em
Rocky 8 com o 13 e finalmente sofreu `pg_upgrade` para o 16. Cada etapa deixou
lixo, e o lixo esta la.

**O cluster e de verdade.** O build roda `initdb`, sobe o postgres, cria roles,
dois bancos, extensoes (`pg_stat_statements`, `pgcrypto`), schema `loja` com
5.000 clientes e 40.000 pedidos, indices, uma tabela particionada, `VACUUM
ANALYZE`, dois replication slots fisicos, forca `pg_switch_wal()` e para o
servidor. Resultado: data directory real, WAL real, **segmentos arquivados de
verdade** em `/var/lib/pgsql/wal_archive`, log do servidor real em
`data/log/postgresql-<dia>.log` e estatisticas reais.

**Configuracao**: `postgresql.conf` do pacote + `include_dir = 'conf.d'` com
arquivos separados por assunto (`10-resources`, `20-wal`, `30-replication`,
`40-logging`, `50-autovacuum`, `60-extensions`, `99-local`), cada um com
comentario dizendo *por que* o valor esta ali. `pg_hba.conf` escrito a mao com
regras por rede, replicacao, `+dba_role` e uma linha antiga comentada.
`pg_ident.conf`, `.psqlrc`, `.pgpass`, `.psql_history` com consultas de DBA.

**RHEL-ismos** (o que diferencia de um Debian): `/etc/sysconfig/pgsql/postgresql`,
drop-in `postgresql.service.d/override.conf` com `OOMScoreAdjust=-900`,
`tmpfiles.d`, `limits.d/30-postgresql.conf`, `sysctl.d` com hugepages e
`vm.overcommit`, perfil de `tuned` proprio, zona do `firewalld` em XML,
`/etc/selinux/config` em **permissive** com o numero do ticket que nunca foi
fechado, `/root/anaconda-ks.cfg` do kickstart original e `/var/log/anaconda/`.

**Backup**: nao existe `pgbackrest` nos repositorios que a maquina usa, entao o
time escreveu o proprio conjunto em `/usr/local/sbin` (`pg-backup.sh` com
`pg_basebackup` + retencao, `pg-wal-archive.sh` como `archive_command` atomico,
`pg-logical-dump.sh`, `pg-restore-test.sh` mensal para a auditoria,
`pg-bloat-report.sh`). Isso e exatamente o que muita empresa faz. Cron em
`/etc/cron.d/pg-backup`, log com uma noite em que o backup **falhou**, diretorios
`base-YYYYMMDD` datados e logrotate.

**Monitoramento**: exporter proprio em `/opt/pg-exporter` (Python + psycopg2,
instalado com `make install`, com `INSTALL_INFO` explicando por que nao e o
oficial), `EnvironmentFile` em `/etc/sysconfig/pg-exporter`, unit, e ainda um
plugin estilo Nagios em `/usr/lib64/nagios/plugins/check_pg_connections` da epoca
do NOC antigo. `pgbouncer` do EPEL com `pgbouncer.ini` em modo transaction.

**O lixo acumulado** (a parte que fixture nenhuma costuma ter):
- `/var/lib/pgsql/13/data` inteiro sobrando, com `PG_VERSION`, config congelada e
  aviso de nao iniciar;
- `/var/lib/pgsql/pg_upgrade_output.d/<timestamp>/` com o log real do pg_upgrade e
  `update_extensions.sql`, mais o `delete_old_cluster.sh` que o pg_upgrade cria e
  que ninguem executou;
- usuario `mysql` ainda existente e travado, `/etc/my.cnf.rpmsave`, `/var/lib/mysql`
  com um LEIA-ME, dump final do MySQL de 2021 comprimido;
- `/etc/cron.d/mysql-backup-DESATIVADO` com tudo comentado;
- `/usr/local/sbin/mysql-backup.sh` que so imprime "nao roda mais" e um
  `pg96-dump.sh` apontando para `/usr/pgsql-9.6/bin` (caminho que nem existe);
- `/etc/ssh/sshd_config.rpmnew` que ninguem mesclou, `CentOS-Base.repo.rpmsave`,
  `exclude=postgresql*` no `dnf.conf`;
- units mascaradas (`nrpe.service` e `mysqld.service` -> `/dev/null`) e o agente
  aposentado em `/opt/nrpe-legado`;
- a rede real esta no keyfile do NetworkManager (`ens192.nmconnection`, o jeito
  EL9), mas o `ifcfg-ens192` do tempo do Rocky 8 continua em
  `/etc/sysconfig/network-scripts/` sem efeito nenhum;
- `/root/MIGRACAO.txt` amarrando tudo isso com os numeros dos tickets abertos.

Os mtimes desses arquivos foram ajustados para as datas certas (2021, 2023, 2025,
abril de 2026), entao `ls -lt` conta a historia sozinho.

## Dockerfile.build — `ci-runner-07.build.example.net`

Ubuntu 22.04, agente de build de uma frota Jenkins. Ponto importante: o
controller conecta por **SSH** ("Launch agents via SSH"), entao **nao existe
daemon/pacote do Jenkins instalado** — o que faz dele um agente e a conta
`jenkins`, o remote root, as toolchains e principalmente os caches. Isso evita
inventar binario proprietario e e como metade das frotas funciona de verdade.

**Toolchains**: OpenJDK 17 (headless) + Maven, Node + npm, Python 3 + pip/venv,
`gcc`/`make`/`libc6-dev` + `ccache` + `pkg-config`, git + git-lfs, docker.io,
shellcheck.

**Caches** (numa maquina real, isso e o grosso do disco): `~/.m2/repository` com
artefatos e arquivos `_remote.repositories`/`.lastUpdated` de verdade,
`settings.xml` apontando para o Nexus interno com credenciais por variavel de
ambiente (`${env.NEXUS_TOKEN}`, nada de segredo no disco), `~/.npm/_cacache`,
`~/.cache/pip`, `~/.gradle`, `~/.sonar/cache`, e `/var/cache/ccache` **de fato
usado**: a ferramenta em C e compilada atraves do `/usr/lib/ccache/gcc` durante o
build (um miss, um hit e uma variante de flags), entao o que `ccache -s` mostra, o
`ccache-stats.txt` do cron e as metricas do textfile collector sao numeros reais
gerados pelo proprio `build-metrics.sh` — nao contadores inventados.

**Workspaces**: tres repositorios git **de verdade** (`git init` + commits) em
`/var/lib/jenkins/workspace/`, com os diretorios `@tmp`/`@script` que o plugin de
pipeline cria ao lado. O workspace `api-service_main` tem `Jenkinsfile`, `pom.xml`,
`Dockerfile`, relatorio do surefire e um **jar compilado de verdade** com
`javac` + `jar` durante o build. Ha tambem um workspace orfao de job ja removido,
preso por um `.build.lock`, com o incidente anotado.

**Fora do apt**, tres sabores, todos normais:
1. pacotes npm globais (`yarn`, `semver`) em `/usr/local/lib/node_modules`;
2. pacotes pip globais (`tox`, `pre-commit`, `yq`) em `/usr/local/bin`;
3. um utilitario em C compilado do fonte com `make && make install`, deixando
   binario em `/usr/local/bin`, man page em `/usr/local/share/man/man1` e a
   arvore de fontes em `/usr/local/src/buildstamp-1.4` com `INSTALL_INFO`.

**Cron de agente** (o mais universal que existe): `docker-prune.sh` diario,
`ci-cleanup.sh`, `workspace-gc.sh` semanal que respeita locks, metricas a cada 5
min. Os logs mostram o prune recuperando 61 GB e o GC pulando o workspace travado.

**Disco e rede**: `/etc/fstab` com `/var/lib/docker` em disco separado (o `vdb1`
que aparece nos logs do prune) e `/var/lib/jenkins` no `vda2`, mais o
`/etc/netplan/50-cloud-init.yaml` com o aviso de "generated by the datasource"
que o cloud-init escreve.

**Resto**: `daemon.json` com mirror do Nexus, registry inseguro interno, pools de
endereco e limite de log; drop-ins do docker com proxy e `OOMScoreAdjust`;
`limits.d` e `sysctl.d` com `fs.inotify.max_user_watches` e `vm.max_map_count`
(webpack e testcontainers, os dois motivos classicos); artefatos de **cloud-init**
(`user-data.txt`, `instance-id`, logs) porque agente e VM de nuvem; proxy de apt
apontando para o apt-cacher-ng; unit `jenkins-agent.service` da epoca do JNLP
deixada no disco **desabilitada** de proposito; `agent-healthcheck.sh` que o
controller chama (roda e passa no build); `syslog` com um OOM kill de build Java.

## O que e placeholder (explicitamente)

Isto sao fixtures, entao nada aqui e segredo de verdade:

- **Senhas**: todas sao literalmente `TROCAR_NO_VAULT`, `__RENDERED_FROM_VAULT__`
  ou `changeme` (o hash do `.htpasswd` e de `changeme`). Nenhuma credencial real.
- **Chaves SSH**: geradas com `ssh-keygen` durante o build. So a **publica** fica
  na imagem (em `authorized_keys`); as privadas correspondentes sao apagadas no
  mesmo `RUN`. Excecao proposital: `/var/lib/jenkins/.ssh/id_ed25519`, porque um
  agente de build tem mesmo uma deploy key local — e uma chave nova e inutil.
- **Certificados**: autoassinados, gerados no build, so a arvore de diretorios
  imita o Let's Encrypt.
- **Arquivos grandes**: os jars do `~/.m2`, os tarballs de backup do Postgres e os
  bundles do frontend sao arquivos-texto marcadores, para nao inchar a imagem.
  Os que importam para inspecao (jar do workspace, WAL arquivado, venv, repos git)
  sao reais.
- **Dominios e IPs**: `example.net`/`example.com` e faixas `10.20.x`/`10.30.x`.

## O que foi realmente exercitado (nao e so arquivo parado)

Cada imagem foi construida e depois testada:

- **web**: `nginx -t` roda **dentro do build** (config invalida quebra a imagem);
  o virtualenv importa Flask e o `wsgi:application` instancia; os nove scripts de
  `/usr/local` passam em `bash -n`; o `telemetry-agent --once` emite JSON lendo
  `/proc`; o `ssl-expiry-check.sh` le o certificado e escreve o `.prom` correto;
  `su` para o usuario `app` funciona.
- **db**: cluster sobe e responde - 5.000 clientes / 40.000 pedidos, extensoes
  `pg_stat_statements`/`pgcrypto`, roles `app_rw`/`app_ro`/`replicator`/`monitoring`,
  dois replication slots e 5 segmentos WAL arquivados de verdade; o `.psqlrc`
  carrega sem erro; o `pg-exporter` compila em Python; os scripts passam em `bash -n`.
  Para subir dentro do container: `mkdir -p /run/postgresql && chown postgres:postgres /run/postgresql`
  e `pg_ctl ... -o "-c shared_buffers=128MB"` (a config de producao pede 4 GB).
- **build**: `agent-healthcheck.sh` roda; `buildstamp` (compilado do fonte com
  `make`) executa; o jar do workspace roda de verdade (`java -jar` imprime
  `api-service 2.7.1`); os tres workspaces tem 2 commits cada em git real; `yarn`,
  `tox`, `pre-commit` e `yq` estao no PATH; o ccache registra hit/miss reais.

## Tamanho das imagens

| imagem | conteudo real (`du -smx /`) | `docker images` nesta maquina | build limpo (`--no-cache`) |
|---|---|---|---|
| `servidor-web` | 565 MB | 800 MB | 2m02s |
| `servidor-db` | 681 MB | 948 MB | 1m57s |
| `servidor-build` | 1139 MB | 1.66 GB | 6m14s |

O daemon desta maquina usa o snapshotter overlayfs do containerd e **infla o
tamanho reportado em ~1,4x**: ele mostra `ubuntu:22.04` como 117 MB quando a
imagem tem ~78 MB. Por isso as duas colunas. Pelo conteudo real as tres ficam
abaixo do teto de 1,5 GB; num daemon com o storage driver classico o
`servidor-build` reporta ~1,2 GB.

O agente de build e naturalmente o maior: JDK 17 (260 MB) e a pilha do docker
(docker.io + containerd + runc, ~264 MB) sao dois tercos dele, e os dois sao o
motivo de a maquina existir. O que deu para cortar sem machucar o realismo foi
cortado: o segundo JVM que o `maven` arrastava, o `awscli` (o Nexus e o destino
dos artefatos, nao o S3), o `g++`/`build-essential` (o compilador C basta para o
ccache e para a ferramenta em `/usr/local`) e o pacote `locales`.

## Detalhes de build que valem registrar

- **O builder desta maquina e o classico (sem BuildKit/buildx).** Nele,
  `RUN <<EOT` *nao falha*: o heredoc e silenciosamente ignorado e o comando nao
  roda. Por isso todo arquivo e escrito com `printf '%s\n' 'linha' ... > destino`,
  que funciona nos dois builders. Cuidado que isso exige: nenhuma linha de
  conteudo pode comecar com `#` sem aspas (o parser do Dockerfile remove linhas de
  comentario mesmo no meio de uma instrucao continuada) — todos os argumentos aqui
  estao entre aspas, entao a linha comeca com `'`.
- `nginx -t` **abre os sockets de verdade**, entao o vhost interno escuta em
  `8080` (com `allow`/`deny`) em vez de amarrar num IP que nao existe no container.
- `initdb -A scram-sha-256` exige senha de superusuario; usa-se
  `--auth-local=peer --auth-host=scram-sha-256`.
- Processo iniciado num `RUN` **nao sobrevive** para o `RUN` seguinte (o commit e
  do filesystem, nao dos processos). Todo o ciclo initdb -> start -> SQL -> stop do
  Postgres acontece num unico `RUN`.
- `pgbackrest` nao existe no EPEL 9 atual; dai os scripts proprios de backup, que
  alias sao mais realistas para uma empresa que nunca padronizou a ferramenta.
- Nenhum dos tres baixa nada de URL inventada: tudo vem de apt/dnf/PyPI/npm ou e
  escrito inline.
- `printf '%s\n' 'texto'` **nao interpreta escapes no argumento**, entao dentro do
  conteudo o `\` vale o que a linguagem de destino espera: `\n` simples em fonte C
  e Python e em `.psqlrc`, mas `\\n` num script bash (onde as aspas duplas comem
  uma barra). Errar isso gera arquivo quebrado sem quebrar o build.
- Ordem importa em duas situacoes que morderam aqui: instalar `maven` junto com o
  JDK faz o apt puxar um **segundo** JVM (openjdk-11, 168 MB) via
  `default-jre-headless` — instalando o JDK antes, num apt separado, a dependencia
  ja esta satisfeita; e escrever `/etc/pip.conf` apontando para o Nexus interno
  **antes** do `pip install` faz o proprio build tentar resolver num host que nao
  existe.
- `git` recusa repositorio de outro dono ("dubious ownership"), entao o agente
  precisa de `safe.directory` — que e exatamente o que se configura num agente de
  CI de verdade.
- `memlock unlimited` em `limits.d` faz o PAM **recusar qualquer `su`** dentro de
  container sem `CAP_SYS_RESOURCE`. No `db` as duas linhas ficaram comentadas com
  o motivo (huge pages nao reservadas), que e uma situacao comum de verdade e
  mantem a imagem utilizavel.
